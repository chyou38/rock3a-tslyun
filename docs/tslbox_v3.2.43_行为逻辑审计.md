# tslbox v3.2.43 行为逻辑审计

## 结论

哨兵链路现在是同一套状态机，能正常用：

**归档完成 → 解一帧哨兵缩略图 → 飞书自动推送 → 车机不写入/USB 断开后再做视频预缓冲和转码。**

车机断开 USB 后页面仍显示“哨兵录像中”的问题已定位并修复，不是网络问题。

## 状态矩阵

| 车机状态 | 归档 | 哨兵缩略图 | 飞书推送 | 视频预缓冲/转码 | 行车锁显示 |
|---|---|---|---|---|---|
| OTG 连接，车机正在写哨兵 | 继续，最高优先 | **允许解一帧** | 允许，发带封面卡片 | 禁止 | 哨兵录像中 · 未锁定 |
| OTG 连接，车机正在写行车记录 | 继续 | 非哨兵背景缩略图让路 | 允许，但封面可能为空；视频回落卡片 | 禁止 | 行车中 · 已锁定 |
| 车机不写，或 OTG 已断开 | 继续 | 正常生成 | 正常推送 | 允许，立即恢复 | 已开启 · 车机空闲 |

## 这次修的三个点

1. **断连后哨兵状态不复位**
   - `write-cat.json` 的 `ts` 会被 `tesla-live-sync` 定时刷新，旧逻辑只看“文件新 + driving=false”就判定为停车哨兵录像。
   - 结果：车机已经断开 USB，页面仍一直显示“哨兵录像中”。
   - 修复：`sentry_writing_only()` 和 `parked_recording()` 先看 OTG 主机实际连接，再看最近 3 分钟是否有车机写入；断开立即返回空闲。
   - `car_active_for_usb()` 也加了 OTG 连接门禁，断开后行车锁立即复位。

2. **转码总闸不完整**
   - 新增 `get_variant()` 总闸：已有缓存直接返回；需要新转码时，车机写入或归档搬运期间一律回退原文件。
   - 覆盖后台预缓冲、飞书视频、用户下载/导出/播放所有路径。
   - 飞书非哨兵视频在车机写入或 `usb_sync_busy()` 时不再转码，直接回落缩略图卡片。
   - 哨兵仍然只解一帧缩略图，不转码视频。

3. **预缓冲取消条件补齐**
   - `prewarm_loop`、`night_hw_loop` 的运行中取消判断都补上 `usb_sync_busy()`。
   - 归档一旦开始，正在跑的预缓冲会暂停/退出，不和车机写入、归档抢 I/O。

## 剩余边界

- 归档完成的判定仍是“最新文件 20 秒静默 + live-sync 的 `__pending__` 清零”，不是车机显式发一个 done 信号。当前实机验证够用；如果要更严格，需要 live-sync 侧补一个归档完成标记。
- 车机写入期间，**已有缓存副本**仍会被播放/下载使用；这不会触发新转码，符合“不转码”的约束。没有缓存时会回退原文件，下载体积可能变大，但车机写入优先。
- 页面每秒刷新一次行车锁状态；升级后如果还看到旧文案，刷新一次页面即可。
